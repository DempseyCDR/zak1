# Research: Single-source admission pricing (P7-R10)

All items resolved; no NEEDS CLARIFICATION remain. The four scope decisions were locked in `/speckit-clarify`
(spec §Clarifications, 2026-08-24); this file records the resolution/mechanism choices that follow.

## R1 — Storage: a dedicated `admission_prices` table

**Decision**: A dedicated `admission_prices` table (`series_id`, `label`, `amount_cents`, `sort_order`,
`effective_date`, `created_at`), NOT an extension of `series_parameters`.

**Rationale**: A sliding scale is a variable number of **club-labeled** tiers edited as a coherent set;
`series_parameters.kind` is a **closed enum** (caller/sound_tech/musician/rent/ongoing/seed_float) that does
not model tier labels. A dedicated table keeps the parameter enum clean while reusing the same effective-dating
idea. (Clarified 2026-08-24.)

**Alternatives**: extend `series_parameters` with an `admission` category — rejected: strains the kind enum and
mixes admission with staff-pay/expense rows.

## R2 — Resolution: a revision is a batch of tiers sharing one `effective_date`

**Decision**: All tiers of one pricing revision share a single `effective_date`. To resolve an event's price:
take the **maximum `effective_date ≤ event date`** for that series, and return **all tiers at that
`effective_date`**, ordered by `sort_order`. No tiers with an effective_date ≤ the event date → no pricing.

**Rationale**: A sliding scale is edited as a whole (add/remove/reorder tiers together), unlike the per-label
independent charges of `resolveOngoingTotalCents` (feature 011). Batch-by-effective_date makes "the price on
date X" unambiguous and preserves history (past revisions are never mutated; a change inserts a new batch with
a later effective_date). Editing = insert a new revision; the newest ≤ the event date wins.

**Alternatives**: per-label latest-effective (the ongoing-charges model) — rejected: makes tier removal and
"the current full scale" ambiguous; a coherent scale is better versioned as a batch.

## R3 — Per-event override: flat, via `events.advertised_price_cents`

**Decision**: `resolveEventPricing` returns a **flat** override when `events.advertised_price_cents` is
non-null; otherwise it resolves the series tiers for the event's date. Removing the override reverts to the
series default. No per-event tier set in v1. (Clarified 2026-08-24.)

**Rationale**: Reuses the field 018/B27 already added; most specials advertise a single door price. YAGNI.

## R4 — `PublicPricing` and the derived card summary

**Decision**: A discriminated union rendered on every surface:
`type PublicPricing = { kind: "flat"; amount: number } | { kind: "tiers"; tiers: { label: string; amount: number }[] } | null`
(amounts in dollars). The **card summary** is `pricingSummary(p)`: `flat → "$12"` (or `"Free"` when the flat
amount is `0`); `tiers →` a concise range `"$5–$15"` over the **distinct non-zero** amounts (single non-zero →
`"$12"`); `null → no price`. The detail and landing render the full tier list; the card renders the summary.
Both come from the **same** `PublicPricing`, so they cannot disagree (SC-001).

**Configured-free vs unconfigured** (the 019 `$0`-vs-`null` distinction, applied here): a **non-empty** tier
set whose amounts are **all `$0`** is *configured free* — `PublicPricing` stays `{ kind: "tiers" }` (non-null)
and `pricingSummary` returns **"Free"** (the non-zero range is empty, so fall through to Free rather than an
empty string). Only an **unconfigured** series (no tiers effective on/before the date, no override) is `null`
→ **no price shown**. Never conflate the two: a free-but-configured series must read "Free", not blank.

**Rationale**: Deriving the summary (never storing it) is the single-source invariant in code; distinguishing
configured-`$0` from unconfigured mirrors `resolveParameterCentsOrNull` (feature 019) and prevents a genuinely
free event from looking like "price unknown".

## R5 — "Musicians free" and "family cap" are tiers

**Decision**: Modeled as ordinary tiers — a `$0` "Musicians" tier, a "Family cap" tier with its amount — so
they render from the one source. No separate fields/flags. The card summary ignores `$0`/cap tiers for the
min of the range where it would mislead (min is the lowest **non-zero** paid tier; `$0` still shows in the
detail list). *(Detail decision; card shows the paid range, detail shows every tier including free.)*

## R6 — Standing-schedule sentence: a `series.schedule_sentence` column

**Decision**: A nullable `schedule_sentence text` on `series`, curated by staff, rendered on the series
landing. Carries the DST-dependent English start time as authored text. No recurrence engine; event rows are
still generated by the existing 013 generator. (Clarified 2026-08-24.)

**Rationale**: One sentence per series co-located with the series; lighter than a 051 content page.

## R7 — Capability & audit reuse

**Decision**: Admission-pricing and schedule-sentence edits are gated by the existing **`parameter.write`**
capability (already gates rate/expense/door parameters; scoped for treasurer/FS, global for organizer/
super_user). Each write records an `audit_events` row via `recordAudit` with a new kind
`admission_pricing.set`. No new capability, no bespoke audit table. (Clarified 2026-08-24.)

**Rationale**: Same actors who set staff rates set admission prices; `recordAudit` (used by 051/052/053) gives
a queryable audit row without a new table.

## R8 — Surfaces & the literals removed

**Decision**: Render `PublicPricing` on the event **card** (summary), the event **detail** (tiers), and the
series **landing** (the series' current tiers, resolved as of today) + the schedule sentence. Remove the
hand-typed literals: the community landing's `landingContent.ts` "Cost: $5 per person, with a $15 family cap"
line, and the event card/detail's direct `advertisedPrice` figure (now folded into `PublicPricing`).

**Rationale**: FR-004/FR-011 — the surfaces that currently hard-code prices must read the single source. The
**printable calendar** named in R10 does not exist yet and is out of scope; `PublicPricing` is the form a
future calendar would consume.
